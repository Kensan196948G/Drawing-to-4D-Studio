# 01 MVP Scope — Drawing-to-4D Studio Phase 1

版: v1.0（2026-11-18） / 状態: 設計承認待ち

## 1. 目的と価値

| 項目 | 内容 |
| --- | --- |
| 目的 | 手元の2D施工計画図（DXF）と工程表（CSV）から、施工順序が伝わる4Dを短時間で作り、説明に使えるようにする。 |
| 利用者 | 施工計画担当 1名（PCブラウザ、1280×800以上）。 |
| 解決課題 | 2D図面と工程表を頭の中で重ねる負担、4D専用ソフトの3Dモデリングと紐付けの手間、説明資料の作り直し。 |
| 提供価値 | 取り込み → 工種確認 → 標高 → 3D → 4D を、ブラウザだけで半自動で完結。図面は外部送信しない。 |
| 成功の測り方 | サンプル図面で、取り込みから4D再生までを10分以内に完了できる。主要レイヤの工種推定がそのまま使え、修正が辞書に反映される。 |

## 2. 主要フロー（1〜3）

### F1 取り込みから4D再生（中核・縦断スライス）

- 開始: DXFと工程表CSVがある。
- 操作: 2ファイルを置く → 工種候補を確認 → 標高を確認 → 3D生成 → 再生。
- 期待: 工程の日付に応じて部材が順に現れ、視点を変えられる。
- 保存: 図面要素・工程・割当・標高・辞書をブラウザへ保存。
- 受入: サンプルで 8工種・29部材、2027/04/01〜2028/03/24 の範囲で再生。

### F2 保存と再開

- 操作: 「保存」→ 案件名 → 保存。「開く」→ 一覧から復元。
- 期待: 部材数・工種・標高・辞書が一致し、同じ4Dが再現される。
- 受入: 保存→再読込で `parts.length`、工種別件数、標高が一致。

### F3 辞書の改善

- 操作: 手動で工種を修正し「このレイヤ名を辞書に登録」。
- 期待: 同じレイヤ名の図面で信頼度100%の自動割当。
- 受入: Layer3 を 045 に修正→再推定で 100%。

## 3. 対象（In Scope）

- 取り込み: ASCII DXF（R12〜R2000相当、LINE/LWPOLYLINE/POLYLINE/CIRCLE/ARC/TEXT/MTEXT/BLOCK/INSERT）、工程表CSV（UTF-8/Shift_JIS、ヘッダあり/なし、Excelシリアル日付）。
- 抽出: レイヤ、閉じた輪郭、円、文字注記、標高注記。
- 推定: レイヤ名・工種コード・文字注記・同形繰り返しによる工種候補（辞書ベース）。
- 確認: 工種の確定・除外・一括確定、辞書学習。
- 標高: 注記の抽出と一括反映、手動修正、進行方向（延長/1つずつ/積み上げ/即時）。
- 3D: 閉じた平面輪郭の押し出し（方式A）、円柱、開いた輪郭の自動補正（0.5mまたは周長1%以内）。
- 4D: 日付スライダー、再生、速度、視点プリセット、部材強調、工程ストリップ。
- 保存: ブラウザ保存（localStorage）。API接続時はPostgreSQLへも保存（任意）。
- 検証環境: Cloudflare Tunnel 経由の Preview、ローカルPostgreSQL、Read/Write確認。
- 品質: TypeScript strict、ESLint、Vitest（単体・結合）、Playwright（E2E）、CI、Secret scan。

## 4. 対象外（Out of Scope）

| 項目 | 理由 | 扱い |
| --- | --- | --- |
| DWG直接、SXF、PDF、Excel、MS Project XML、J-LandXML | Phase 2以降 | UIに「第2段階」と表示 |
| AIによる工種推定 | Phase 2 | 辞書ベースで代替 |
| Blender MP4、IFC/glTF出力 | Phase 2 | 画面録画はブラウザ機能で代替可能 |
| 方式B（断面形状の法線押し出し） | 実装量と入力要件が増える | Backlog |
| 複数ユーザー、Entra ID SSO | 個人MVP | Cloudflare Accessで前段保護 |
| 本番環境・本番DB・本番DNS変更 | 指示で対象外 | 実施しない |
| 数量算出・干渉確認・BIM/CIM代替 | 構想案で非対象と明記 | 画面に注記 |

## 5. 仮定（要件が不足しているため置いたもの）

| # | 仮定 | 根拠 | 変更時の影響 |
| --- | --- | --- | --- |
| A-01 | 対象工種は構想案の10工種（010〜090） | サンプル工程表と一致 | マスタ・辞書・色の変更 |
| A-02 | 工程表CSVの列は 工種コード・工種名・開始日・終了日 | サンプルCSV | パーサとUIの列対応 |
| A-03 | 座標単位は $INSUNITS に従い m へ換算 | サンプルは m | スケールの変更 |
| A-04 | 平面図の X を延長方向、Y を奥行き、標高を Y軸（3D）とする | サンプルの形状 | カメラ・クリップ方向 |
| A-05 | 図面は1案件1ファイル（平面＋断面を同一DXFに含む） | サンプル | 複数ファイル対応が必要 |
| A-06 | 保存はブラウザ優先、サーバ保存は任意 | オフライン要件 | 同期方式の変更 |
| A-07 | Preview は Cloudflare Access で保護する | 既存プロジェクトの運用 | 代替はアプリトークン |

## 6. 受入条件（MVP完了）

1. F1〜F3 がローカルで動作し、証拠（コマンド・終了コード・画面）が残る。
2. サンプルで 8工種・29部材が生成される。
3. 保存→再読込で同一の4Dが再現される。
4. 空DBから Migration → Seed → 起動が再現できる。
5. 型検査・Lint・単体・結合・E2E・Build・Secret scan が成功する。
6. Critical/High の既知問題がない。
7. PR が作成され、CI が緑で、auto-merge の状態を GitHub 上で確認できる。
8. Cloudflare Preview に配備され、対象commitと対応し、F1 を実操作できる。
9. README・設計・DB・API・Test・Deployment が更新されている。
10. 制限・復旧・Backlog・次の一手が記録されている。

## 7. 縦断スライスの定義

最初の実装単位は **F1 の画面→API→永続化→再読込** ではなく、Phase 1 の性格上 **画面→ブラウザ内処理→保存→再読込** とする。
API/DB は「辞書共有・案件カタログ・サーバ保存」の任意機能として後段に追加し、SPA単体で F1〜F3 が成立することを先に確認する。
これにより、構想案の「完全オフライン」を壊さずに、指示された DB 連携も検証できる。
